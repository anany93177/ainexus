# Day4_Runtime_Context_Parameter_Injection_And_Citation_Display_Guidelines

## 1. Introduction

The purpose of runtime context injection is to dynamically populate Prompt Templates with real-time, user-specific, and session-specific data at the exact moment of execution. Prompt-level context management is critical for ensuring that the Large Language Model (LLM) receives highly relevant, personalized, and bounded information. By enforcing strict parameter injection guidelines, the system eliminates prompt ambiguity, minimizes hallucinations, and ensures that AI responses are consistently anchored in the authoritative lesson context. Furthermore, rigorous context management facilitates the accurate generation of citations, establishing trust and traceability within the Nexus Learning & Certification Platform.

---

## 2. Runtime Variable Standards

The following table defines the standardized Runtime Variables used for prompt injection. All variables must be strictly typed and validated before Prompt Assembly.

| Variable Name | Data Type | Required / Optional | Source | Description |
| :--- | :--- | :--- | :--- | :--- |
| `{{user_query}}` | String | Required | User Interface | The exact raw input or question provided by the learner. |
| `{{lesson_context}}` | String | Required | Content Retrieval System | The authoritative text, definitions, or transcripts relevant to the current module. |
| `{{lesson_metadata}}` | JSON | Optional | Content Database | Structured data (e.g., module ID, difficulty, topic tags) related to the lesson. |
| `{{conversation_history}}` | Array[Object] | Optional | Session Storage | The recent multi-turn dialogue history necessary to maintain contextual continuity. |
| `{{citations}}` | Array[String] | Optional | Content Retrieval System | Reference links or source IDs mapping back to the injected lesson context. |
| `{{confidence_score}}` | Float | Optional | Intent/Retrieval Engine | The system's confidence (0.0 - 1.0) regarding the retrieved context relevance. |
| `{{session_context}}` | JSON | Required | Identity Management | Contextual data about the active session (e.g., timezone, device, language). |
| `{{learning_progress}}` | JSON | Optional | LMS Backend | Metrics indicating the user's completion rate and past performance. |
| `{{prompt_id}}` | String | Required | Prompt Registry | The unique identifier of the active Prompt Template being executed. |
| `{{intent}}` | String | Required | Intent Detection Model | The classified purpose of the user's query (e.g., clarification, quiz, summary). |

**Injection Mechanism:** Every Runtime Variable is parsed from its respective source and injected into the Prompt Template using the platform's runtime templating engine. Variables are strictly mapped to their corresponding placeholders, ensuring that the LLM processes a fully resolved, context-rich prompt.

## 3. Prompt Runtime Variable Mapping

The mapping of Runtime Variables into Prompt Templates follows a structured, sequential workflow to guarantee integrity and determinism.

**Workflow:**

1. Prompt Template
2. Runtime Variables
3. Context Injection
4. Prompt Assembly
5. LLM Execution
6. Response Validation

**Stage Explanations:**

1. **Prompt Template:** The baseline instruction set is retrieved from the Prompt Registry based on the detected intent. It contains immutable instructions and mutable placeholders (e.g., `{{user_query}}`).
2. **Runtime Variables:** The system aggregates all necessary data (user inputs, database records, session states) into a standardized key-value payload.
3. **Context Injection:** The templating engine sanitizes the Runtime Variables and securely maps them to their respective placeholders within the template.
4. **Prompt Assembly:** The engine finalizes the string, locking all variables into place to produce the final, executable prompt payload.
5. **LLM Execution:** The assembled prompt is transmitted to the language model for inference.
6. **Response Validation:** The generated output is parsed and evaluated against expected schemas, Citation Standards, and safety bounds before being returned to the user.

## 4. Prompt Execution Pipeline

The complete Prompt Execution Pipeline ensures end-to-end traceability from user input to final output.

**Execution Flow:**

1. User Query
2. Intent Detection
3. Prompt Registry Lookup
4. Prompt Template Selection
5. Runtime Variable Assembly
6. Lesson Context Injection
7. Prompt Assembly
8. LLM Execution
9. Citation Formatting
10. Response Validation
11. Final Response

**Stage Responsibilities:**

*   **User Query:** Captures the raw input securely from the frontend interface.
*   **Intent Detection:** Classifies the query to determine the appropriate system action and persona.
*   **Prompt Registry Lookup:** Queries the centralized Prompt Registry using the detected intent and context parameters.
*   **Prompt Template Selection:** Retrieves the optimal, version-controlled Prompt Template.
*   **Runtime Variable Assembly:** Fetches and structures all required and optional Runtime Variables (session, progress, metadata).
*   **Lesson Context Injection:** Integrates the authoritative knowledge base excerpts required to answer the query.
*   **Prompt Assembly:** Compiles the template and variables into a single, cohesive string.
*   **LLM Execution:** Sends the assembled prompt to the model and streams/receives the response.
*   **Citation Formatting:** Extracts source references from the model's output and formats them according to UI standards.
*   **Response Validation:** Checks the output for hallucinations, inappropriate content, and structural integrity.
*   **Final Response:** Delivers the sanitized, cited, and validated response to the learner.

## 5. Prompt Runtime Injection Rules

*   **Required Variables:** Prompt Assembly will immediately fail and throw an exception if any required variable (e.g., `{{user_query}}`, `{{session_context}}`) is null or missing.
*   **Optional Variables:** Missing optional variables must gracefully default to an empty string, empty array, or safe fallback value without disrupting the template structure.
*   **Missing Variable Behaviour:** If a critical context variable cannot be retrieved (e.g., database timeout), the system must abort assembly and trigger a fallback safety prompt or error message to the user.
*   **Runtime Priority:** Explicitly provided user context takes precedence over implicitly derived session history in the event of variable conflicts.
*   **Variable Sanitization:** All string inputs (especially `{{user_query}}`) must be aggressively escaped and sanitized to prevent prompt injection attacks or control character execution.
*   **Immutable Prompt Sections:** System instructions, core constraints, and behavioural guardrails cannot be overridden by any Runtime Variable.
*   **Runtime Override Rules:** Under strict administrative or testing conditions, specific Runtime Variables may be overridden via secure header flags; however, this is strictly prohibited in production.
*   **Injection Validation:** Post-injection, the assembled prompt is scanned for unresolved placeholders (e.g., lingering `{{...}}` syntax) to prevent broken prompt execution.

### 5.1 Runtime Variable Priority Hierarchy

The precedence of runtime information during Prompt Assembly is defined below. Higher-priority components override lower-priority information whenever conflicts occur.

1. Core System Prompt
2. Lesson Context
3. User Query
4. Conversation History
5. Learning Progress
6. Optional Runtime Metadata

## 6. Citation Standards

To maintain academic and platform integrity, the system enforces the following enterprise Citation Standards:

*   **Inline Citation Rules:** Citations must be placed directly after the factual claim they support, formatted as superscripts or bracketed numbers (e.g., `[1]`).
*   **Multiple Citation Rules:** When multiple sources support a single claim, they must be combined into a single bracket, separated by commas (e.g., `[1, 3]`).
*   **Citation Ordering:** Citations must be numbered chronologically as they appear in the generated response.
*   **Citation Confidence:** Citations are only appended if the source context has a retrieval confidence score exceeding the minimum platform threshold (e.g., > 0.75).
*   **Missing Citation Behaviour:** If the model makes a factual claim but fails to generate a citation, the Response Validation stage must flag the response for review or append a generic "Source verification pending" disclaimer.
*   **Unsupported Citation Behaviour:** If a generated citation ID does not match any ID provided in the `{{citations}}` Runtime Variable (hallucinated citation), the response must be rejected or the invalid citation stripped.
*   **Duplicate Citation Removal:** The formatting engine must deduplicate identical source references and consolidate them under a single citation ID.
*   **Citation Formatting Rules:** The final payload must include a mapping object linking citation IDs to their full metadata (Source Title, Lesson Name, URL) enabling the frontend to render interactive tooltips.

## 7. Prompt Validation Framework

The Validation Framework acts as a firewall between Prompt Assembly and the final user response.

**Validation Pipeline:**

1. Runtime Variable Validation
2. Context Validation
3. Prompt Validation
4. Citation Validation
5. Response Validation
6. Output Approval

**Stage Explanations:**

*   **Runtime Variable Validation:** Ensures all variables are correctly typed, sanitized, and present before injection.
*   **Context Validation:** Verifies that the injected `{{lesson_context}}` meets minimum relevance thresholds and length constraints.
*   **Prompt Validation:** Scans the fully assembled prompt for unresolved placeholders, unauthorized template modifications, and prompt injection attempts.
*   **Citation Validation:** Cross-references citations generated in the LLM output against the authoritative sources provided in the context.
*   **Response Validation:** Evaluates the final LLM output for formatting errors, harmful content, and adherence to system constraints.
*   **Output Approval:** The final gate where the validated payload is packaged and cleared for transmission to the frontend.

---

## 8. Runtime Error Handling

*   **Missing Context:** Return a predefined conversational response indicating that the platform lacks sufficient information to answer the specific query.
*   **Missing Variables:** Abort Prompt Assembly, log a critical system error, and inform the user that their request could not be processed.
*   **Invalid Runtime Variables:** Reject the variable, fallback to default if optional, or abort execution if required, triggering an alert for data corruption.
*   **Corrupted Metadata:** Strip corrupted metadata from the injection payload and proceed with the core text context to maintain service availability.
*   **Empty Citation Array:** Process the prompt but strictly instruct the LLM (via system instructions) not to make definitive factual claims without provided sources.
*   **Invalid Prompt Selection:** Fall back to a default, highly constrained safety template to handle the interaction securely.
*   **Runtime Validation Failure:** Suppress the LLM output entirely and return a standard "We encountered an issue processing your request" error to the user.
*   **Low Confidence Responses:** If the retrieval or generation confidence falls below the threshold, clearly flag the output to the user as an "Estimated or Unverified" response.
